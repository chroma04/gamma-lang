# Self-hosting and the bootstrap seed

`gamma`, the Gamma compiler, is written in Gamma (`compiler/`) and compiles itself. This
page explains how a machine with only a C compiler gets it (the bootstrap seed), what keeps
that chain trustworthy, and how the compiler was first built and the Rust reference
implementation it was built against was retired. How the compiler is organized is in
[`architecture.md`](architecture.md).

## Bootstrapping from the seed

`bootstrap/seed/` holds the C that the compiler generates for its own sources: units that
share a header (`gammac.h`), with the runtime in `gammac.rt.c`. `bootstrap/build.sh` builds
`gamma` from it with nothing but a C compiler (see [`bootstrap/README.md`](../bootstrap/README.md)):

```sh
bootstrap/build.sh            # writes target/bootstrap/gamma
```

1. The script compiles the seed into `gamma0`.
2. `gamma0` builds the compiler of the current sources (`gamma1`).
3. `gamma1` builds the current sources again, so that the result, `gamma`, is the current
   compiler as generated by itself and not by the seed's.

`CC` selects the C compiler and `JOBS` the number of units compiled at once; the build takes
a few minutes. After a change to `compiler/`, `lib/` or `runtime/`, `tools/test.sh` rebuilds
`target/bootstrap/gamma` with the previous one (incrementally, through the cache of compiled
units), and so does

```sh
GAMMA_STD=$PWD/lib/std GAMMA_RUNTIME=$PWD/runtime target/bootstrap/gamma build compiler -o <out>
```

### The fixed point

A compiler built by another one (stage 1) builds a second (stage 2), and the C that stage 2
generates for the compiler's sources is byte-identical to the C stage 1 generated: the
compiler built by itself is a fixed point. Stage 2 also checks the sources exactly as
stage 1 does.

```sh
GAMMA_STD=lib/std ./gamma1 build compiler -o gamma2
GAMMA_STD=lib/std ./gamma1 build compiler --emit-c -o stage1
GAMMA_STD=lib/std ./gamma2 build compiler --emit-c -o stage2
cmp stage1.c stage2.c                    # identical
```

The compiler's manifest (`compiler/gamma.toml`) builds it in the Checked mode: optimized,
with its overflow and bounds checks on. It runs about two and a half times as fast as a Debug
build of it. A Debug build (`gamma build --mode=debug compiler`) reports the calls that led
to a trap, which helps when the compiler itself fails.

The `selfhost` suite of the test harness checks the fixed point, that the compiler's unit
tests pass (in the Debug mode, which checks them for leaks) and its sources are formatted,
that the split C form of the seed builds, and that a packaged release runs from its
installed layout.

### One seed for every host

The seed works on every 64-bit little-endian Unix-like system that Gamma supports: Linux and
macOS on x86-64 and AArch64. The compiler asks the system for the operating system and
architecture it runs on (`uname`) instead of fixing them when it is compiled, so its
generated C is the same on every such host.

### What the seed is

The seed is generated, never edited. `bootstrap/seed/SOURCE` names the git trees of
`compiler/`, `lib/` and `runtime/` it was generated from, and the seed is exactly the C that
the compiler of those sources, built by itself, generates for them. `bootstrap/verify.sh
[GAMMA0]` checks this: it compiles the seed (or uses the given `gamma0`), has the result
generate C for the named trees and compares it with the seed. It needs the git history that
holds those trees. CI runs it on x86-64 Linux, where the seed is generated, and checks that
the build from the seed reaches the fixed point on Linux (x86-64 and AArch64) and macOS.
Reviewing the seed therefore means reviewing the Gamma sources it names, and each seed is
generated by the compiler of the one before it.

### Refreshing the seed

The seed needs refreshing only when the compiler's sources stop building with it, that is,
when they start using something the seed's compiler does not have. After committing the
change to `compiler/`, `lib/` or `runtime/`, `tools/refresh-seed.sh [GAMMA]` regenerates the
seed from the committed sources and writes the new `SOURCE`. A change that has the compiler's
own sources use a new language feature comes in two steps: first teach the compiler the
feature and refresh the seed, then use the feature in `compiler/`. Changes that do not need a
refresh leave the seed alone, which keeps the repository from growing with every change.
[`contributing.md`](contributing.md#the-bootstrap-seed) has the steps.

## History

### How it was built: the parity contract

The compiler was built in stages next to a reference implementation in Rust (`src/`). While
the reference existed, each stage of the compiler had to produce output **byte-identical** to
the reference's for the same input. Every stage has a stable textual form that made this
checkable:

| Stage | Compared output |
| --- | --- |
| lexer | the token dump of `lex`, and its diagnostics |
| parser | the syntax tree dump of `parse --dump`, and its diagnostics |
| modules and packages | the module graph of `modules`, and its diagnostics |
| declarations | what `decls` prints for every top-level declaration, and its diagnostics |
| bodies | the typed program of `tir`, and its diagnostics |
| checking | the diagnostics of `check`, in the human format |
| back end | the output and exit status of the compiled programs |
| interpreter, REPL, test runner, formatter, `doc`, lint and fix, language server, package manager, targets and caches | the output, exit status and files of the same command in both |
| bootstrap | the C that the compiler generates for itself, built by itself |

Diagnostics were compared in the JSON format (`--diag-format=json`), which carries every part
of a diagnostic: the message, the primary span, labels, notes and fixes. The comparison ran
over every `.gm` file in the repository: the conformance tests (including the ones written to
provoke errors), the standard library, the examples, the benchmarks and the compiler's own
sources. A parity test ran on every `cargo test`, so a change to either implementation that
made them disagree failed the build.

Parity was strict on purpose. It turned the whole test corpus of the reference into a test
suite for the new compiler without writing a single new expectation, and it made the
reference the specification of everything the language specification leaves to
implementations: message texts, spans and recovery after errors. Those messages, spans and
recoveries are now defined by the compiler in `compiler/` and its tests.

The stages were, in order: the lexer; the parser with its error recovery and the syntax tree
dump; modules and packages; the checker, in two parts (declarations, then bodies with
compile-time evaluation and generics); the C back end, a port of the reference's with the
same representation of values and the same use of the runtime; and the bootstrap. A stage
that covered a large part of the language grew over several steps. Until it was complete, the
compiler reported each construct it could not handle yet with an error that started `cannot`,
and the parity test compared only the programs without such an error; the number of programs
compared could only grow, because the test failed if it dropped below a floor that was raised
as the compiler learned more. The tools followed: the interpreter, the REPL, the test runner,
the formatter, the documentation generator, lint and fix, the language server, the package
manager, targets, modes and caches, and the Windows build.

### Retiring the reference

When every stage was complete and the compiler built itself, the Rust implementation had no
remaining job, and keeping it would have meant keeping two compilers in step for every
language change. It was retired in steps. First nothing was built from it for users: the
`gamma` command became the compiler in `compiler/`, and the release workflow and the
bootstrap needed no Rust. Then the tests stopped comparing with it: the parity tests were
replaced by the expectations of the repository's own suites, and the Rust test suites by a
test harness written in Gamma. Last, the code was deleted. Its final state is the git tag
`rust-reference-final` (commit `d09a1a6`). The language change after that point, spec §7.7
(the element of `in` and its members are compared at one type, joined as `if` branches are),
is the first made without the reference.

**The final cross-check.** On that commit, the compiler built by the Rust `gamma`
(`gamma build compiler`, a release build of the Rust crate) and the compiler built from the
bootstrap seed generate byte-identical C for the compiler's sources
(`gamma build compiler --emit-c` with `GAMMA_STD=lib/std` as a relative path): 61,253,433
bytes, SHA-256 `0584d6b50c606eb43f55f644abe299295c163fece27a82d609c99f0fb5b1831b`. Together
with the seed check in CI (each seed is exactly what the previous seed's compiler generates
for the sources it names), this ties every future seed to the last compiler the Rust
implementation built. Nothing in the chain of compilers depends on a binary that cannot be
rebuilt from the source before it, which is a form of diverse double-compiling.

**What replaced each kind of check:**

| Parity check against the reference | Now |
| --- | --- |
| token, syntax tree, module, declaration and typed-program dumps; diagnostics | the expectations in `tests/conformance/` (`//~ ERROR` annotations and the golden `.tokens` and `.ast` files), which every change is tested against |
| output and exit status of compiled programs | the same expectations (`.stdout`, `//! exit`), checked for every `run` test |
| interpreter against the reference's interpreter | the interpreter against C: each `run` test runs in both and must agree, and `tools/difftest` compares them on generated programs under gcc and clang |
| formatter, `doc`, lint and fix, language server, package manager, REPL, test runner | the suites `fmt`, `doc`, `lint`, `fix`, `lsp`, `pkg`, `repl` and `testing_cli`, which test the executable named by `GAMMA_TEST_COMPILER` |
| targets, modes, caches | the suites `cross`, `freestanding`, `wasi`, `native_build` and `lanes` |
| bootstrap | the `selfhost` suite (the fixed point), the seed check (`bootstrap/verify.sh`) and the cross-check above |
| robustness on malformed input | fuzzing the compiler itself (`fuzz/`, see [`contributing.md`](contributing.md#fuzzing)) |

The suites that tested Rust internals (the Cranelift back end, the internal compiler error
report, the Rust interpreter's child processes and deadline, its foreign calls, the layout of
an installed Rust build) were removed with them, and so was the `//! cranelift: skip`
directive.
